Git Basics

What is Git? — Core Concepts

Git is a version control system that tracks every change in your project files. Think of it as a time machine for your code.

GitConcept
3 areas you must know:
Working Directory — your actual files on disk (where you write code).
Staging Area (Index) — files you've marked to be committed (git add).
Repository (.git) — the saved snapshot history (git commit).
Working Directory
Edit files ──git add──→ Staging Area
Prepare snapshot ──git commit──→ Repository
Saved history ──git push──→ GitHub
Remote backup
⚙️

Install & First-Time Setup

Configure Git with your identity before anything else — every commit records who made it.

GitSetup
terminal — one-time setup
# ── 1. Check if Git is installed ──
$ git --version
git version 2.44.0

# ── 2. Set your name (shows in commits) ──
$ git config --global user.name "Rahim Ahmed"

# ── 3. Set your email (must match GitHub account) ──
$ git config --global user.email "rahim@example.com"

# ── 4. Set default branch name to 'main' ──
$ git config --global init.defaultBranch main

# ── 5. Set VS Code as default editor ──
$ git config --global core.editor "code --wait"

# ── Verify your config ──
$ git config --list
✅
Run these commands once after installing Git. They apply globally to all your projects on this machine.

.gitignore — What NOT to Track in Flutter

Tell Git to ignore generated files, build outputs, and secrets. Flutter creates a default .gitignore automatically with flutter create.

GitFlutter
The .gitignore file lives in your project root. Any path listed here is completely ignored by Git — never committed, never pushed. Critical for keeping secrets out of GitHub and keeping your repo small.
# ── Flutter build outputs (never commit these) ──
build/
.dart_tool/
.flutter-plugins
.flutter-plugins-dependencies

# ── IDE files ──
.idea/
.vscode/
*.iml

# ── Android / iOS generated ──
android/.gradle/
ios/Pods/
ios/.symlinks/

# ── Secrets & Environment (NEVER commit these!) ──
.env
google-services.json     # Firebase config
GoogleService-Info.plist  # Firebase iOS config
*.keystore                # Android signing key
key.properties            # Android key passwords

# ── Dart generated ──
*.freezed.dart
*.g.dart                  # json_serializable output

# ── pubspec.lock: commit for apps, ignore for packages ──
# pubspec.lock
🔥
Never commit google-services.json, key.properties, or .env to GitHub. If you do accidentally, the secret is compromised — rotate it immediately.
Core Git Commands
📸

add · commit · status · log

The four commands you'll use every single day. Stage changes, save snapshots, check what's changed, and view history.

GitDaily Use
daily workflow
# ── See what changed ──
$ git status
  modified:   lib/main.dart
  untracked:  lib/screens/home.dart

# ── Stage a specific file ──
$ git add lib/main.dart

# ── Stage ALL changed files at once ──
$ git add .

# ── Stage parts of a file interactively ──
$ git add -p lib/main.dart

# ── Commit with a message ──
$ git commit -m "feat: add home screen UI"

# ── Stage + commit tracked files in one step ──
$ git commit -am "fix: resolve API null error"

# ── View commit history ──
$ git log
$ git log --oneline          # compact view
$ git log --oneline --graph  # with branch graph

# ── See exactly what changed in files ──
$ git diff                   # unstaged changes
$ git diff --staged          # staged changes
Good commit messages use a prefix:
feat: new feature  ·  fix: bug fix  ·  refactor: code cleanup  ·  style: UI/formatting  ·  docs: documentation  ·  chore: dependencies, config

Branching — Work Without Breaking Main

Branches let you build features in isolation. The main branch stays clean and deployable at all times.

GitBranching
Rule of thumb: never code directly on main. Create a new branch for every feature, bugfix, or experiment. Merge back when done.
branch commands
# ── List all branches ──
$ git branch
* main
  feature/login

# ── Create new branch ──
$ git branch feature/task-screen

# ── Switch to a branch ──
$ git checkout feature/task-screen

# ── Create AND switch in one command (preferred) ──
$ git checkout -b feature/task-screen
# OR modern syntax:
$ git switch -c feature/task-screen

# ── Rename current branch ──
$ git branch -m new-name

# ── Delete a merged branch ──
$ git branch -d feature/task-screen

# ── Delete unmerged branch (force) ──
$ git branch -D feature/old-experiment

# ── See all branches including remote ──
$ git branch -a
Branch naming convention for Flutter projects:
feature/login-screen  ·  fix/null-safety-crash  ·  refactor/task-provider  ·  release/v1.2.0
🔀

merge · rebase — Combining Branches

Two ways to integrate changes from one branch into another. Both have different use cases.

GitMerge
git merge — creates a new "merge commit" that joins two branches. History shows the branch clearly. Use for team projects and feature branches.
merge
# Go to main first
$ git checkout main

# Merge feature branch into main
$ git merge feature/task-screen
Merge made by 'ort' strategy.

# Delete the branch after merge
$ git branch -d feature/task-screen
git rebase — replays your commits on top of another branch. Creates a linear history with no merge commits. Use for keeping local feature branches up to date.
rebase
# On feature branch, rebase onto main
$ git checkout feature/task-screen
$ git rebase main

# Continue after resolving conflicts
$ git rebase --continue

# Abort rebase if needed
$ git rebase --abort
⚠️
Never rebase commits that have already been pushed to a shared GitHub branch.
⚡

Merge Conflicts — How to Resolve

A conflict happens when two branches change the same line differently. Git marks the conflict and waits for you to decide.

GitConflict
What a conflict looks like in a Dart file:
lib/main.dart — conflict markers
<<<<<<< HEAD          ← your current branch (main)
  home: const HomeScreen(),
=======              ← separator
  home: const TaskScreen(),
>>>>>>> feature/task-screen  ← incoming branch
steps to resolve
# 1. Git tells you which files conflict
$ git status
both modified: lib/main.dart

# 2. Open the file, manually choose what to keep:
#    - Keep your version (HEAD)
#    - Keep their version (incoming)
#    - Keep both / rewrite
#    Delete ALL conflict markers (<<<, ===, >>>) when done

# 3. Stage the resolved file
$ git add lib/main.dart

# 4. Complete the merge
$ git commit -m "merge: resolve home screen conflict"

# VS Code shows a 3-way diff UI for conflicts —
# use "Accept Current" / "Accept Incoming" buttons
↩️

Undo & Fix Mistakes

Git lets you undo almost anything. The right command depends on how far the change went.

GitUndo
undo commands
# ── Discard changes in working directory (PERMANENT) ──
$ git checkout -- lib/main.dart
# Modern syntax:
$ git restore lib/main.dart

# ── Unstage a file (keep changes, just un-add) ──
$ git restore --staged lib/main.dart

# ── Fix last commit message (before pushing) ──
$ git commit --amend -m "fix: corrected commit message"

# ── Add forgotten file to last commit (before pushing) ──
$ git add lib/forgotten.dart
$ git commit --amend --no-edit

# ── Undo last commit, KEEP the changes ──
$ git reset HEAD~1        # default: --mixed (changes go to working dir)
$ git reset --soft HEAD~1  # changes go back to staging

# ── Undo last commit, DISCARD the changes (DANGEROUS) ──
$ git reset --hard HEAD~1

# ── Safe undo: creates a new "undo" commit (for pushed commits) ──
$ git revert abc1234    # use the commit hash from git log

# ── Stash: temporarily save unfinished work ──
$ git stash              # save dirty state
$ git stash pop          # restore it
$ git stash list         # see all stashes
$ git stash drop         # delete top stash
⚠️
git reset --hard permanently deletes uncommitted work. Use with extreme caution. Prefer git revert for commits already pushed to GitHub.
GitHub — Remote & Collaboration
☁️

Connect Local Repo to GitHub

Push your local Flutter project to a new GitHub repository for backup and collaboration.

GitHubRemote
First time only: create an empty repo on GitHub (no README, no .gitignore), then link it to your local project with these commands.
connect & push
# ── Add GitHub as the remote named 'origin' ──
$ git remote add origin https://github.com/yourname/my_app.git

# ── Verify remote was added ──
$ git remote -v
origin  https://github.com/yourname/my_app.git (fetch)
origin  https://github.com/yourname/my_app.git (push)

# ── First push: set upstream tracking ──
$ git push -u origin main
Branch 'main' set up to track 'origin/main'.

# ── From now on, just: ──
$ git push

# ── Change remote URL (e.g. moved repo) ──
$ git remote set-url origin https://github.com/newname/my_app.git

# ── Remove a remote ──
$ git remote remove origin
🔄

push · pull · fetch — Sync with GitHub

Keep your local and remote repos in sync during solo work and team collaboration.

GitHubSync
push · pull · fetch
# ── Push: send local commits to GitHub ──
$ git push                           # push current branch
$ git push origin feature/login     # push specific branch
$ git push --force-with-lease        # safe force push (after rebase)

# ── Pull: fetch + merge in one command ──
$ git pull                           # pull current branch
$ git pull origin main               # pull specific remote branch
$ git pull --rebase                  # pull and rebase instead of merge

# ── Fetch: download changes WITHOUT merging ──
$ git fetch                          # see what's new on remote
$ git fetch origin

# ── Push a new branch to GitHub ──
$ git push -u origin feature/new-screen

# ── Delete a remote branch ──
$ git push origin --delete feature/old-branch
fetch vs pull: git fetch downloads remote changes but doesn't touch your local files. git pull = git fetch + git merge. Use fetch when you want to inspect changes before merging.
📬

Pull Requests (PR) — The GitHub Workflow

A Pull Request is a proposal to merge your feature branch into main. It triggers code review before anything is merged.

GitHubTeam
How a PR works: you push your feature branch → open a PR on GitHub → teammates review your code → approve → merge into main. This is the standard team workflow for every real Flutter project.
complete PR workflow
# ── Step 1: Create feature branch ──
$ git checkout -b feature/profile-screen

# ── Step 2: Do your work, then commit ──
$ git add .
$ git commit -m "feat: add user profile screen"

# ── Step 3: Push branch to GitHub ──
$ git push -u origin feature/profile-screen

# ── Step 4: Go to GitHub.com ──
#    → You'll see a "Compare & pull request" button
#    → Write a PR title and description
#    → Request reviewers
#    → Click "Create pull request"

# ── Step 5: After teammates review & approve ──
#    → Click "Merge pull request" on GitHub
#    → Delete the branch on GitHub

# ── Step 6: Update your local main ──
$ git checkout main
$ git pull
$ git branch -d feature/profile-screen  # clean up locally
✅
Good PR description includes: what changed, why it changed, screenshots of UI changes, and how to test it. Flutter PRs should always mention if pubspec.yaml was changed.

Fork — Contribute to Open Source

Fork = your personal copy of someone else's repo on GitHub.

GitHub
fork workflow
# 1. Fork on GitHub.com (click Fork button)
# 2. Clone YOUR fork
$ git clone https://github.com/YOU/flutter_pkg.git

# 3. Add original as 'upstream'
$ git remote add upstream \
  https://github.com/ORIGINAL/flutter_pkg.git

# 4. Keep your fork up to date
$ git fetch upstream
$ git merge upstream/main

# 5. Push changes & open PR to original

Team Collaboration — Stay in Sync

Working with other developers on the same Flutter project. How to handle updates from teammates without breaking your own work.

GitHubTeam
daily team routine
# ── Morning: always pull before starting work ──
$ git checkout main
$ git pull                # get teammates' latest commits
$ git checkout feature/my-branch
$ git merge main          # bring updates into your branch

# ── If teammate pushed to main while you were coding ──
$ git stash               # save your uncommitted work
$ git pull                # get updates
$ git stash pop           # restore your work

# ── See what a teammate committed ──
$ git fetch
$ git log origin/main --oneline

# ── Check out a teammate's branch locally ──
$ git fetch
$ git checkout feature/teammate-branch
$ flutter pub get         # always run after checkout!

# ── After pulling: always check if packages changed ──
$ git pull
$ flutter pub get         # if pubspec.yaml was changed
💡
After any git pull or branch switch, run flutter pub get if pubspec.yaml or pubspec.lock changed. Also run flutter clean if you get strange build errors after pulling.

GitHub Actions — Auto-Run Flutter Tests on Every Push

CI/CD: automatically run flutter test and flutter analyze every time code is pushed to GitHub.

GitHubCI/CD
Create a file at .github/workflows/flutter.yml in your project. GitHub automatically detects and runs it on every push and PR.
.github/workflows/flutter.yml
name: Flutter CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Flutter
        uses: subosito/flutter-action@v2
        with:
          flutter-version: '3.22.0'

      - name: Install dependencies
        run: flutter pub get

      - name: Analyze code (lint)
        run: flutter analyze

      - name: Run tests
        run: flutter test

      - name: Build APK (verify it compiles)
        run: flutter build apk --release
✅
After adding this file and pushing, go to GitHub → Actions tab to see the workflow run. A green ✅ means all tests passed. PRs will show a status check before merging.

cherry-pick — Copy a Single Commit

Apply one specific commit from another branch without merging the whole branch.

Advanced
cherry-pick
# Get the commit hash from git log
$ git log --oneline
a3f8c21 fix: null safety crash in TaskModel
b72d015 feat: add search bar

# Cherry-pick ONLY the fix commit onto current branch
$ git cherry-pick a3f8c21

# Cherry-pick a range of commits
$ git cherry-pick a3f8c21..b72d015
Use case: a critical bug was fixed on a feature branch but main needs it now — cherry-pick brings just that fix.

Git Aliases — Shortcuts

Define short commands for things you type every day.

AdvancedProductivity
~/.gitconfig
# Set aliases via terminal
$ git config --global alias.st status
$ git config --global alias.co checkout
$ git config --global alias.br branch
$ git config --global alias.lg \
  "log --oneline --graph --all"

# Now use short form:
$ git st          # = git status
$ git co main     # = git checkout main
$ git lg          # = pretty log

SSH Keys — Push Without Password Every Time

Set up SSH once and never type your GitHub password again when pushing.

GitHubSSH
SSH setup — one time
# ── 1. Generate SSH key pair ──
$ ssh-keygen -t ed25519 -C "you@example.com"
  (press Enter to accept defaults)

# ── 2. Copy the PUBLIC key ──
$ cat ~/.ssh/id_ed25519.pub
  (copy the entire output)

# ── 3. Add to GitHub ──
#    GitHub.com → Settings → SSH and GPG keys
#    → New SSH key → paste → Save

# ── 4. Test the connection ──
$ ssh -T git@github.com
Hi yourname! You've successfully authenticated.

# ── 5. Change existing repo from HTTPS to SSH ──
$ git remote set-url origin \
  git@github.com:yourname/my_app.git

# Now push works without password:
$ git push
